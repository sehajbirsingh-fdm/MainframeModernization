## Findings

### BLOCKER-001: Authentication bypasses OAuth2/JWT requirements with static token matching

- Evidence: `specs/002-inqacc-account-inquiry-modernization/checklists/requirements.md:246` requires OAuth2 bearer-token auth; `specs/002-inqacc-account-inquiry-modernization/checklists/requirements.md:265` requires expiry validation; `src/api/src/main/java/com/bankofz/inqcust/api/inqacc/security/BearerTokenAuthenticationFilter.java:22` and `src/api/src/main/java/com/bankofz/inqcust/api/inqacc/security/BearerTokenAuthenticationFilter.java:23` define hardcoded accepted tokens; `src/api/src/main/java/com/bankofz/inqcust/api/inqacc/security/BearerTokenAuthenticationFilter.java:45` and `src/api/src/main/java/com/bankofz/inqcust/api/inqacc/security/BearerTokenAuthenticationFilter.java:53` authenticate solely by string equality.
- Why it matters: This does not validate JWT signature/issuer/expiry and creates a credential-replay path if a static token is exposed. It also cannot meet the documented expired-token behavior.
- Suggested fix: Replace custom token string checks with Spring Security OAuth2 resource server JWT validation (`spring-boot-starter-oauth2-resource-server`) and claim-to-authority mapping. Add explicit tests for expired token, invalid signature, and missing token behaviors.
- Recommended owner: Security

### MAJOR-001: 401 error contract is collapsed into one generic code, missing required distinctions

- Evidence: `specs/002-inqacc-account-inquiry-modernization/checklists/requirements.md:278` requires `MISSING_AUTHENTICATION`; `specs/002-inqacc-account-inquiry-modernization/checklists/requirements.md:279` requires `INVALID_TOKEN`; `specs/002-inqacc-account-inquiry-modernization/checklists/requirements.md:280` requires `TOKEN_EXPIRED`; `src/api/src/main/java/com/bankofz/inqcust/api/inqacc/controller/AccountInquiryExceptionHandler.java:35` and `src/api/src/main/java/com/bankofz/inqcust/api/inqacc/controller/AccountInquiryExceptionHandler.java:37` always return `ERR-002`; tests at `src/api/src/test/java/com/bankofz/inqcust/api/inqacc/controller/AccountInquiryControllerTest.java:119` and `src/api/src/test/java/com/bankofz/inqcust/api/inqacc/controller/AccountInquiryControllerTest.java:133` assert only `ERR-002` and contain no expired-token case.
- Why it matters: Contract-level error semantics are not traceable per requirement acceptance criteria, reducing diagnosability and violating requirement-specific response behavior.
- Suggested fix: Introduce distinct authentication failure categories and map each to required codes/messages; add targeted controller tests for all required 401 variants.
- Recommended owner: Dev Lead

### MAJOR-002: OpenAPI artifacts in source are misaligned with INQACC contract endpoint

- Evidence: INQACC contract defines `/accounts/{sortcode}/{accountNumber}` in `specs/002-inqacc-account-inquiry-modernization/contracts/openapi.yaml:23`; runtime resource OpenAPI still describes INQCUST `/api/v1/customers/{sortCode}/{customerNumber}` in `src/api/src/main/resources/openapi.yaml:7`; alternate API file is broad OpenBanking content not scoped to INQACC in `src/api/src/main/api/openapi.yaml:2`.
- Why it matters: API consumers, QA, and generated clients can target stale/wrong paths and schemas, and this violates profile expectations for schema/contract updates aligned with changed behavior.
- Suggested fix: Consolidate to one authoritative OpenAPI artifact for deployed API surface, align endpoint/security/error schemas with INQACC, and add a failing test if runtime OpenAPI drifts from feature contract.
- Recommended owner: Dev
